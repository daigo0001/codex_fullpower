# テスト仕様書 · 社内問い合わせ管理

架空案件の初回公開用の記入例。以下の結果は期待値。実行時は候補イメージのダイジェスト、Git コミット、実行環境、データセット、実施時刻、担当、判定とログ参照先を残す。

## 実施範囲と完了条件

- API 単体では権限・入力値・状態遷移の表を実行する。組み合わせの競合と原子性はステージング相当の Azure SQL を使う。
- ステージングで認証、問い合わせの検索・詳細・登録、状態変更、管理者の閲覧、定時連携を通す。申請者A・B、窓口担当C、管理者Dは架空アカウントを使う。
- 重大な認証・認可・整合性の失敗があれば公開判定を保留する。制約、テスト証跡、責任者をリリース判定で照合する。

## T-005 状態変更の詳細

共通準備は対象 IT-1028 を対応中に戻し、窓口担当Cと同じ範囲の別の窓口担当Eでログインすること。テスト前の状態行、履歴件数、監査件数と ETag を記録する。記録に秘密情報を添付しない。

| ケース | 操作 | 期待する HTTP 応答 | DB で確認すること |
| --- | --- | --- | --- |
| T-005-A 正常 | 最新 ETag で対応中 → 解決を送信 | 200、解決、新 ETag | 状態・履歴・変更監査が同時に確定 |
| T-005-B 競合 | C と E が同じ ETag を読み、別リクエストで解決へ並行更新 | 200 と412が1件ずつ | 有効な変更1件で履歴と変更監査は各1件追加 |
| T-005-C 条件欠落 | If-Match を送らない | 428 | 状態・履歴・変更監査に変化なし |
| T-005-D 遷移違反 | 対応中 → 終了を API へ指定 | 409 | 状態・履歴・変更監査に変化なし |
| T-005-E 操作範囲 | 申請者Aの読み取れる問い合わせの状態更新を試す | 403 | 状態・履歴・変更監査に変化なし |
| T-005-F 途中失敗 | 隔離試験で履歴書き込みにだけ検証用の異常を与える | 500 と照会ID | 状態更新と監査が全体でロールバック。運用ログの分類コードを確認 |

## 非機能と運用

- T-008。人工的に作った1万件の問い合わせを使い、30人相当で読取80%の混合負荷を与える。一覧と詳細それぞれの p95 が1.5秒以内。シナリオ比率、応答分布、エラー率、試験した版を残す。
- T-009。権限マトリクスと画面状態を照合する。認可拒否でデータが更新されず、ログ閲覧が権限別に制限され、ログ本文に入力や秘密情報が含まれないことを確認する。
- T-010。バックアップを隔離環境へ復元する。使用可能になった最新データから障害想定時刻までが1時間以内、障害想定時刻からログインと主要操作の確認までが4時間以内。復元したチケット、履歴、社員の件数とサンプルを照合する。
