# 教材構成と判定方法

初めに窓口の依頼を読み、確認したい質問を書き足す。確認結果を要件 ID、受入条件、スコープに整理し、同じ ID を画面・API・DB・テストまで追う。実装前の技術選定と、運用と公開の判断も同じ案件の制約で考える。

## 各章で判断すること

| 章 | 使う根拠 | 残すもの |
| --- | --- | --- |
| 01〜02 | 利用者、業務頻度、既存連携、納期、受入条件 | 顧客への確認と自分の要件 |
| 03〜05 | 要件 ID、画面の状態、データ、認証、復旧・予算 | 画面・技術・基盤のレビューと採用理由 |
| 06〜08 | 成果物、完了条件、担当者、実績、前提、休日 | WBS、三点見積、ガントチャート |
| 09〜11 | 遅延・変更・事故の影響、確認済みの事実、代替案 | 変更案、報告、課題表、AI 成果物の指摘 |
| 12 | 別案件の制約と学んだ判断方法 | 要件、設計・見積、計画、リスク、リリース判定 |

完成例を読んだ後、自分の判断を書き、チェック結果と比較して修正できる。演習のフィードバックは教材に定義した条件と模範例で返す。入力者の業務における正しさ、技術調査の完了、見積の実現可能性は、参照した資料や試験で確認する。

問い合わせの状態変更の例では、REQ-005 → SCR-02 → API-05 → `Tickets.RowVersion` → T-005 と追跡する。画面のボタン表示、API の認可、競合で更新が上書きされないことはそれぞれ別の確認項目となる。

## 手法と資料の粒度

- 段階を区切る進め方では、インターフェイス確定、顧客承認、移行計画の合意を節目にする。承認待ちも計画に入れる。
- 反復型では最初に危険な前提を小さい範囲で検証できる。仕様が固まった部分から設計と実装を繰り返す。
- アジャイルでは短い周期で動くものを見せ、受入条件と優先度を更新する。契約やリリース審査で必要な記録は作業の完了条件に含める。

個人では目的・判断・試験結果を1ページでも残す。2〜3人では引き継ぐ成果物とレビュー担当を明示し、5人以上では機能や権限境界ごとに責任を明確にする。現場の設計書には対象環境、契約、承認、実データを扱う基準、保守能力を反映する。
