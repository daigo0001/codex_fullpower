# Codex Lab

ポータルから、9つのブラウザーアプリを開けます。

- **RDB Design Lab** (`/database/`) は、備品貸出を題材に、テーブル設計、制約、インデックス、同時更新を学べる教材です。
- **Incident Lab** (`/incidents/`) は、Web アプリの障害を題材に、調査、対応、復旧確認を練習できる教材です。
- **Azure Network Atlas** (`/azure/`) は、Azure の VNet と通信経路を、構成図とシナリオで学べます。
- **Dev Blueprint** (`/planning/`) は、Web アプリを企画からリリースまで進める実例と資料を読める作業スペースです。WBS の編集や設計資料の出力もできます。
- **Crypto Lab** (`/crypto/`) は、暗号化・パスワードハッシュ・ZIP・署名を用途別に学べるページです。
- **MVC Flow** (`/mvc/`) は、ASP.NET Core MVC のミドルウェア、ルーティング、フィルター、アクションの処理順を可視化します。
- **Flow Atlas** (`/network/`) は、DNS から HTTP 応答までの通信経路と順序を可視化します。
- **Header Guard** (`/security/`) は、HTTP レスポンスヘッダーの防御設定を点検します。
- **YOSORA / 夜空** (`/yosora/`) は、観測地と日時から星空を描き、天体の観測計画と記録を作れます。

## Docker で起動

Docker と Docker Compose が使える環境で、リポジトリのルートから実行します。

```sh
docker compose up --build
```

ブラウザーで [localhost:8080](http://localhost:8080) を開きます。終了するときは `Ctrl+C` を押して `docker compose down` を実行します。8080 番ポートをほかで使用している場合は、`YOSORA_PORT=8081 docker compose up --build` で公開ポートを変更できます。

## GitHub Pages で公開

1. リポジトリの **Settings → Pages** で、**Build and deployment → Source** を **GitHub Actions** に設定します。
2. **Actions → Deploy Codex Lab to GitHub Pages → Run workflow** から、`main` を選んで実行します。以降は `public/` の変更を `main` に push すると自動更新されます。

公開先の URL は **Settings → Pages** で確認できます。このリポジトリの標準 URL は `https://daigo0001.github.io/codex_fullpower/` です。Docker 版と GitHub Pages 版では、お気に入りと観測ノートの保存領域が別になります。

## RDB Design Lab の使い方

1. **設計の考え方** と **テーブルと制約** で、備品貸出の業務ルール、主な検索、テーブルの関係を結びつけます。
2. **インデックスを試す** で、用途に合わせてクエリと候補のインデックスを選択します。PostgreSQL で架空の貸出データを使って取得した実行計画を比較できます。
3. **同時更新を試す** で、2人の貸出操作を一手ずつ追い、部分ユニークインデックスが重複をどう防ぐか確認します。
4. **AI とスキーマ変更** で、既存データとマイグレーションの確認、権限、AI の提案と確定記録を分ける設計を学べます。

ブラウザーだけで利用できます。実行計画はサンプルの計測結果で、実際の選択はデータ分布や PostgreSQL の設定によって変わります。

計測を再現する場合は、検証用の PostgreSQL 17 データベースに `test/fixtures/database-index-demo.sql` を読み込みます。同じセッションで `jit = off`、`max_parallel_workers_per_gather = 0` を設定し、画面の候補インデックスを一つずつ作成して、選んだ SQL に `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY OFF)` を付けて実行します。

## Incident Lab の使い方

1. デプロイ直後の 502、Blob の 403、貸出処理の 504、ログインループの中からシナリオを選びます。
2. ログ、メトリクス、構成、変更履歴を見比べ、仮説と対応を選びます。フィードバックを読んで、別の証拠を確認してからやり直せます。
3. 復旧を裏付ける確認項目を選びます。演習の最後に、見た証拠、原因、対応、再発防止案と自分のメモを Markdown に保存できます。

ケースはすべて架空で、演習の進行やメモは現在のタブ内で扱います。リセットまたは再読み込みで初期状態に戻ります。

## Azure Network Atlas の使い方

1. Application Gateway による受信、NAT Gateway による送信、Private Endpoint への接続、Private DNS のリンクがない接続、ハブ・スポーク間の通信から選びます。
2. 再生、ステップ送り、またはシーケンス図の行で経路を進めます。各ステップの送信元、宛先、名前解決、ルートや許可の判断を確認できます。ステップの詳細では注目する OSI 層を強調します。
3. **基礎ガイド** で VNet とサブネット、NSG とルート、各サービスを比較できます。**OSI 7層**の解説からシナリオの該当ステップに移動できます。特定のステップは共有リンクで開けます。

構成、アドレス、所要時間は説明用の例です。ブラウザー内で動作し、Azure アカウントやリソースの作成は不要です。

## Dev Blueprint の使い方

1. **企画からリリースまで** (`/planning/#delivery`) で、備品貸出アプリの情報収集、コア要件、技術要件、設計、実装・テスト、公開と運用を順に確認します。**ひとり開発** と **チーム開発** で各段階の確認方法を切り替えられます。
2. フォルダ構成から記入例の Markdown を1件ずつ保存できます。ZIP を展開すると `docs/README.md` と、各段階の資料を入れた6つのフォルダができます。
3. **WBS を作る** で「備品貸出管理」の例を使うか、新規の計画を作ります。成果物、完了条件、担当、期限、工数、前提タスク、状態を編集し、表計算ソフト向けの CSV または復元用の JSON を保存できます。
4. **設計テンプレート** で記入例とひな形を切り替え、要件、画面、詳細、インフラ、フォルダ構成の資料を Markdown で保存できます。

WBS の下書きはブラウザー内に保存されます。別の端末やブラウザーで続きを編集する場合は JSON で移します。チームに配る資料には CSV と Markdown を使えます。

## Crypto Lab の使い方

- **パスワードハッシュ**では、同じ入力に2つの異なるソルトを付け、PBKDF2-HMAC-SHA-256 のハッシュが異なることと、保存済みレコードとの照合を試せます。
- **共通鍵・公開鍵暗号**では、ブラウザー内の鍵で AES-256-GCM の暗号化・復号・改変検出を試せます。
- **ZIP の暗号化**では、ZipCrypto、AES ZIP、ヘッダーを暗号化した 7z の違いを確認できます。**署名・TLS**では SHA-256、HMAC、署名の役割を比較します。

実験は HTTPS または `localhost` で動きます。入力や鍵はアプリから外部に送信せず、永続保存も行いません。例の文字列で試せます。ZIP は方式や互換性を学ぶセクションで、ファイルの作成や展開は行いません。

## MVC Flow の使い方

1. 通常の GET、認可での短絡、入力エラーの再表示、アクションの例外、ビュー描画の例外からシナリオを選びます。
2. 再生、ステップ送り、またはシーケンス図の各行で処理を進めます。図ではミドルウェアと MVC の境界、リクエストとレスポンスの方向、処理が打ち切られる位置を確認できます。
3. 「ステップを共有」で同じシナリオとステップを開けるリンクをコピーできます。

説明用に設定した ASP.NET Core MVC のパイプラインをブラウザーで再現しています。処理時間は例示値です。実際の順序や短絡時のレスポンスはアプリの構成によって変わります。[ミドルウェアの公式ドキュメント](https://learn.microsoft.com/ja-jp/aspnet/core/fundamentals/middleware/) · [フィルターの公式ドキュメント](https://learn.microsoft.com/ja-jp/aspnet/core/mvc/controllers/filters)

## Flow Atlas の使い方

1. HTTPS 初回アクセス、CDN キャッシュヒット、HTTP/3、DNS 解決失敗からシナリオを選びます。
2. 再生ボタン、スライダー、または「リクエストの流れ」の各行で移動します。経路図は通信の向きを示し、詳細欄ではプロトコルと送受信するデータの例を確認できます。
3. 「ステップを共有」で、選んだシナリオとステップを直接開けるリンクをコピーできます。

たとえば初回アクセスと CDN キャッシュヒットを比べると、キャッシュがある場合は CDN エッジから応答が返り、オリジンへの通信が省けます。図のアドレス、通信内容、所要時間は説明用の例です。アプリはリクエストの送信やパケットの取得を行いません。

## Header Guard の使い方

1. 自分のサイトを開き、ブラウザーの開発者ツールの **Network** タブで確認したいレスポンスのヘッダーをコピーします。画面のサンプルでも試せます。
2. Header Guard に貼り付けて点検します。CSP、HSTS、フレーム埋め込み制御、Cookie の属性などを確認し、確認結果や見直し箇所を Markdown で保存できます。

入力は端末のブラウザー内で処理します。レポートにはヘッダーの元の値や Cookie の値を含めません。判定はコピーしたレスポンスを対象にした設定の目安です。サイト全体の脆弱性評価や TLS 設定の検査は対象外です。

## YOSORA の使い方

1. 観測地と日時を指定します。星図は中心が天頂、外周が地平線で、上が北、左が東です。
2. 星図や天体一覧で天体を選ぶと、高度や方位、時間による高度の変化を確認できます。
3. 気になる天体を「お気に入り」に保存し、観測した内容を「観測ノート」に残せます。

東京で 2026 年 11 月 21 日の 21:00 を選ぶと、アンドロメダ銀河が高度約 81° にあります。天体を選んで再生ボタンを押すと、星図と高度グラフで夜間の動きを追えます。

観測リストと日誌はブラウザーのローカルストレージに保存されます。ブラウザーや公開ポートを変えると、別の保存領域が使われます。

観測しやすい時間帯は、天体の高度が 20° 以上で、太陽の高度が −12° 以下の区間です。天体の位置と時刻は目安です。大気差や恒星の固有運動は計算に含まれません。実際の見え方は、天気、光害、月明かり、その場所の地形や建物にも左右されます。

## 開発とテスト

Node.js 24 以上があれば、Docker を使わずに起動できます。追加の npm パッケージは不要です。

```sh
npm test
npm start
```

サーバーの稼働確認には `curl --fail http://localhost:8080/healthz` を使えます。

## データと画像

- 恒星の座標、等級、色の区分は David Nash（AstroNexus）の [HYG Database v4.1](https://github.com/astronexus/HYG-Database) に基づきます。星図とカタログ用に恒星を選別し、座標の桁数や色を表示用に変換しました。
- 星雲や星団などの座標と等級は Mattia Verga の [OpenNGC](https://github.com/mattiaverga/OpenNGC)（M45 を含む補遺も使用）から選んだものです。
- `public/js/faint-stars.js` と `public/js/catalog.js` の上記データベース由来のデータは [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) で提供します。
- 惑星の位置は、1800 年から 2050 年までの [NASA/JPL の近似軌道要素](https://ssd.jpl.nasa.gov/planets/approx_pos.html) を使って計算します。月の位置には Jean Meeus『Astronomical Algorithms』第 47 章の主要な周期項を使い、観測地点からの視差を補正します。
- アプリカードと YOSORA の背景画像は生成画像です。
